# Требования к скиллу, генерирующему страницы поддержки и приватности

## 1. Контекст и назначение

Скилл создаёт и поддерживает две статические HTML-страницы в папке `pages/` внутри репозитория мобильного/веб-проекта. Затем эти файлы вручную копируются в репозиторий GitHub Pages `andybeardness/andybeardness.github.io` в папку `<slug>/`, где они становятся:

- `https://andybeardness.github.io/<slug>/` — страница поддержки (Support URL для App Store / Google Play)
- `https://andybeardness.github.io/<slug>/privacy.html` — политика конфиденциальности (Privacy URL для сторов)

Эти URL обязательны для публикации в сторах, поэтому пути и якоря должны быть стабильны.

## 2. Входные параметры, которые скилл собирает у пользователя

Обязательные:
- `slug` — kebab-case, используется как имя сабдиректории и в путях ссылок (`/<slug>/...`)
- `name` — отображаемое имя проекта (например, `Formular`, `Korobochka`)
- `tagline` — короткий слоган под названием (1 строка)
- `about` — 1–3 предложения, что делает приложение
- `contact_email` — email для связи (по умолчанию `beardness.andy.dev@gmail.com`)
- `accent_color` — hex-цвет акцента для light-темы; скилл сам подбирает dark-вариант и tint (см. § 5)
- `logo_letter` — одна буква/символ для квадратного логотипа (обычно первая буква имени)
- `data_collection` — структурированное описание, что приложение собирает (см. § 4.2). По умолчанию — «ничего, всё хранится локально».

Опциональные:
- `faq` — массив пар «вопрос/ответ»; если пуст, секция FAQ не рендерится
- `languages` — список локалей i18n. По умолчанию: `[en, ru]`. Полный поддерживаемый набор: `en, ru, de, fr, es, hi, ko, zh`. Английский обязателен и является fallback.
- `effective_date` — дата вступления политики в силу в формате `YYYY-MM-DD`. Если не задана — `TBD` (с напоминанием пользователю обновить перед отправкой в стор).
- `third_party_sdks` — список используемых SDK (analytics, crash reporting, IAP и т.д.) с их собственными privacy-policies. Если пуст — третья секция privacy всё равно остаётся, но с дженерик-формулировкой.

## 3. Структура вывода

```
<project repo>/
└── pages/
    ├── index.html      ← страница поддержки
    └── privacy.html    ← политика конфиденциальности
```

Скилл должен быть **идемпотентным**: повторный запуск с теми же входами даёт тот же файл байт-в-байт. Если файл уже существует и параметры не изменились — не перезаписывать.

## 4. Контент страниц

### 4.1 `pages/index.html` — Support

Обязательные блоки в указанном порядке:
1. **Top bar** — селектор языка (виден только если `languages.length > 1`).
2. **Header** — квадратный логотип с буквой, название, tagline.
3. **About** — секция с описанием приложения (из поля `about`).
4. **Contact us** — строка с email, кликабельная (`mailto:` с пред-заполненной темой вида `<Name> — support request` локализованной).
5. **Legal** — строка-ссылка на `./privacy.html` (с сохранением `?lang=<current>` в query, чтобы язык не сбрасывался при переходе).
6. **FAQ** — секция `<details>/<summary>` со списком из `faq`. Скрывается полностью, если `faq` пуст.
7. **Footer** — копирайт и подпись «Support and feedback» (локализованные).

Поведение:
- Селектор языка: значение применяется немедленно (без перезагрузки), сохраняется в `localStorage` (ключ `<slug>_support_lang`), и пишется в `?lang=` query. Если в URL `?lang=xx` — используется он. Иначе — `localStorage`. Иначе — `navigator.languages`. Иначе — `en`.
- В FAQ-ответах разрешён инлайн-HTML для ссылок (`<a>`); вставляется через `innerHTML`. Контент контролируется владельцем скилла, поэтому XSS-риска нет, но скилл должен оставить комментарий в коде, чтобы будущий редактор это понимал.
- `email_subject` локализуется: каждая локаль имеет свою тему письма.

### 4.2 `pages/privacy.html` — Privacy Policy

Обязательные секции в указанном порядке:
1. **Top bar** — кнопка «← Back» на `/<slug>/` (с сохранением `?lang=`) + селектор языка (если `languages.length > 1`).
2. **Header** — тот же логотип/название, что и на support.
3. **Meta-блок** — Effective date (или `TBD` с пометкой), название приложения.
4. **§ Introduction** — стандартная вводная: «эта политика описывает, как `<Name>` обрабатывает информацию».
5. **§ Information We Collect** — генерируется из `data_collection`:
   - Если ничего не собирается — текст «App does not collect, store, or share any personal data on external servers. All data stays on your device.»
   - Если что-то собирается — структурированный список с категорией, целью и сроком хранения.
6. **§ Third-Party Services** — список из `third_party_sdks` со ссылками на их privacy policies; либо общая формулировка, если список пуст.
7. **§ Children's Privacy** — стандартный текст про детей младше 13 лет.
8. **§ Changes to This Policy** — стандартный текст.
9. **§ Contact** — email-ссылка.
10. **Footer** — копирайт.

Поведение:
- Тот же механизм i18n, что и на support-странице (общий ключ `localStorage`).
- Если `effective_date == TBD`, скилл должен напечатать предупреждение в stdout: «Не забудь проставить реальную effective date перед отправкой в стор».
- Если в `data_collection` упомянуты IDFA / Advertising ID / точная локация / health-данные / контакты — скилл должен предупредить, что для App Store Privacy Nutrition Labels потребуются соответствующие декларации в App Store Connect (это вне html, но скилл должен об этом сказать).

## 5. Визуальные требования (обе страницы)

- **Дизайн-стиль:** iOS Settings-подобный (как у `formular/`): белые/тёмные «карточки» секций со скруглением 14px, разделители 0.5px, заголовки секций мелкими капсами, акцент-цвет для интерактивных элементов.
- **Темы:** обе — `prefers-color-scheme: light/dark`. Никаких toggles темы — только системная.
- **Палитра светлой темы:**
  - `--bg #f2f2f7`, `--surface #ffffff`, `--text #1c1c1e`, `--muted #6c6c70`, `--separator #e5e5ea`
  - `--accent` — из `accent_color`, `--accent-tint` — светлая 10% версия акцента
- **Палитра тёмной темы:**
  - `--bg #000000`, `--surface #1c1c1e`, `--text #ffffff`, `--muted #aeaeb2`, `--separator #2c2c2e`
  - `--accent` — осветлённая версия (примерно +12% lightness), `--accent-tint` — тёмная 15% версия акцента
- **Типографика:** `-apple-system, BlinkMacSystemFont, "SF Pro Text", Roboto, "Helvetica Neue", Arial, sans-serif`. Базовый размер 16px, line-height 1.5.
- **Ширина контента:** `max-width: 720px`, центрирование, паддинги `16px 20px 56px` на мобилке.
- **Логотип:** квадрат 72×72, скругление 18px, акцент-фон, белая буква 32px, лёгкий drop-shadow с альфой акцента.
- **Доступность:**
  - Каждый интерактивный элемент имеет `aria-label`, если визуального текста недостаточно (например, селектор языка).
  - Контраст текст/фон ≥ 4.5:1 в обеих темах.
  - Селектор языка нативный `<select>` (не кастомный JS-дропдаун) ради корректной работы со скринридерами и мобильной клавиатурой.
  - `<html lang>` обновляется при смене языка.

## 6. Технические ограничения

- **Один файл = одна страница.** Никаких внешних CSS/JS/шрифтов/иконок/изображений. CSS — инлайн в `<style>` внутри `<head>`. JS — инлайн в `<script>` перед `</body>`. Каждая страница полностью самодостаточна.
- **Никаких build-шагов и зависимостей.** Файлы открываются напрямую браузером.
- **Без аналитики, трекеров, шрифтов с CDN.** Privacy-страница, которая сама шлёт данные — самообман.
- **`<link rel="icon" href="data:," />`** — чтобы убрать 404 favicon-запрос.
- **Иконки** — emoji (`✉`, `🔒`, `›`) или unicode-символы. Не SVG-файлы, не иконочные шрифты.
- **Никаких inline-стилей в разметке** (`style="..."` в тегах) — только классы и CSS-переменные.
- **HTML валиден** по спецификации HTML5; проходит без ошибок в `html-validate` или аналоге.
- **JS-минимум.** Только то, что нужно для i18n и применения года в `<span id="year">`. Без фреймворков.

## 7. i18n-контракт

- Словари локалей лежат как `const I18N = { en: {...}, ru: {...}, ... }` в `<script>`.
- Каждая локаль содержит **все** ключи; отсутствие ключа = ошибка генерации.
- В разметке тексты заменяются через `data-i18n="key"`. Скилл не оставляет «русский по умолчанию» в HTML — английский всегда исходный, остальные подменяют его JS-ом.
- Привязка `<html lang>`, `document.title` и `email_subject` — при каждом переключении языка.
- Скилл должен предложить пользователю автоматический перевод недостающих локалей (через LLM) и **показать diff** перед записью; пользователь подтверждает.

## 8. Совместимость со store-требованиями

Скилл должен гарантировать, что итоговые страницы удовлетворяют формальным требованиям сторов:
- **App Store**: Privacy URL обязателен, должен быть публично доступен, описывать сбор данных в соответствии с тем, что задекларировано в App Store Connect Privacy Labels. Support URL обязателен, должен содержать способ связаться с разработчиком.
- **Google Play**: Privacy URL обязателен для всех приложений, должен описывать (если применимо) сбор и обмен `personal and sensitive user data` в полном соответствии с Data Safety form.
- Скилл предупреждает (но не блокирует генерацию), если:
  - `effective_date == TBD`
  - в `data_collection` есть категории, требующие явных деклараций в Data Safety / Privacy Labels
  - `contact_email` отличается от обычного `beardness.andy.dev@gmail.com` (на случай опечатки)

## 9. Идемпотентность и обновления

- Скилл хранит сгенерированные параметры в `pages/.skill-manifest.json` (slug, language, accent, hash контента). При повторном запуске сверяет манифест с входами и регенерирует **только то, что изменилось**.
- Если пользователь вручную правил HTML — скилл показывает diff и спрашивает: перезатереть, оставить, или mergить (если возможно — например, дописать новую локаль, не трогая правки в существующих).
- Скилл никогда не удаляет файлы автоматически.

## 10. CLI-интерфейс скилла (рекомендация)

- Первый запуск: интерактивный мастер собирает все параметры, генерирует обе страницы.
- Повторный запуск: показывает текущий манифест, спрашивает что изменить (поле / язык / FAQ-запись / SDK).
- Команды-подкоманды:
  - `init` — первичная генерация
  - `add-lang <code>` — добавить локаль (предлагает авто-перевод)
  - `update-faq` — открыть редактор FAQ
  - `set effective-date <YYYY-MM-DD>` — проставить дату перед релизом
  - `preview` — открыть оба файла в браузере (`open pages/index.html` на macOS)
  - `check` — линт: валидность HTML, наличие всех i18n-ключей, проверка `effective_date != TBD`, контраст палитры.

## 11. Готовые эталонные файлы

Текущий «золотой» пример качества — `formular/index.html` и `formular/privacy.html` в репозитории `andybeardness.github.io`. Скилл должен генерировать файлы того же уровня полировки. Минимальный пример (более простой стиль) — `korobochka/`, но **новый дефолт должен быть на уровне formular**.

## 12. Соглашение о номере билда (iOS и Android)

Номер билда в обеих платформах **привязывается к количеству коммитов** в репозитории проекта. Это даёт монотонно растущий, детерминированный и воспроизводимый билд-номер без ручного ведения счётчика.

- **Источник истины:** `git rev-list --count HEAD` — количество коммитов в текущей ветке от корня.
- **iOS (`CFBundleVersion` / Build):** значение из `git rev-list --count HEAD`.
- **Android (`versionCode` в `build.gradle` / `build.gradle.kts`):** то же значение.
- **Marketing version** (`CFBundleShortVersionString` / `versionName`) — задаётся отдельно вручную (`1.2.3`); привязки к коммитам **нет**.

Правила:
- Билд-номер вычисляется **на CI / в момент сборки**, а не коммитится в репозиторий. Никаких ручных bump'ов в `Info.plist` / `build.gradle` после каждого коммита.
- Если приложение собирается на разных машинах, репозиторий должен быть полностью склонирован (без shallow clone) — иначе счётчик коммитов окажется заниженным и стор отклонит билд как «уже существующий». В GitHub Actions это означает `actions/checkout@v4` с `fetch-depth: 0`.
- Билд-номер монотонен в рамках одной долгоживущей ветки (`main`/`release`). При мерже фича-веток не должно образовываться «дырок» или откатов — следить за тем, чтобы линейная история сохранялась (rebase merges или squash merges).
- Для App Store и Google Play номер билда уникален в пределах версии (App Store) и в пределах приложения (Play). Подход с коммитами это обеспечивает естественным образом.

Реализация по платформам:

**iOS (Xcode build phase или fastlane):**
```sh
BUILD_NUMBER=$(git rev-list --count HEAD)
/usr/libexec/PlistBuddy -c "Set :CFBundleVersion $BUILD_NUMBER" "$INFOPLIST_FILE"
```

**Android (`build.gradle.kts`):**
```kotlin
val gitCommitCount = providers.exec {
    commandLine("git", "rev-list", "--count", "HEAD")
}.standardOutput.asText.get().trim().toInt()

android {
    defaultConfig {
        versionCode = gitCommitCount
        versionName = "1.2.3"
    }
}
```

**Flutter (`pubspec.yaml` + CI):**
- `version: 1.2.3+<BUILD>` — `<BUILD>` подставляется CI'ем перед `flutter build`:
  ```sh
  BUILD=$(git rev-list --count HEAD)
  flutter build ipa --build-number=$BUILD
  flutter build appbundle --build-number=$BUILD
  ```

Скилл должен (опционально, по запросу пользователя при `init`):
- Сгенерировать соответствующий build phase script / Gradle snippet / CI-step под платформу проекта.
- В `pages/.skill-manifest.json` пометить, что соглашение применено, чтобы при последующих запусках напомнить о нём.
- Предупредить, если в CI используется shallow clone (`actions/checkout@v4` без `fetch-depth: 0`) — нужен полный клон.
